# Decision memo — ADR-0009's Gemma claim appears to be false

**Status:** pending owner decision. Not a ruling. Written by Lane C, 2026-08-21,
at Eric's request, as ground-truth-plus-options — not as a recommendation
that resolves itself into an edit. No existing file was changed to produce
this memo.

**Read `docs/NEEDS-ERIC.md` item 10 alongside this** — the coordinator flagged
the same defect the same night this memo was requested, with its own three
options and a recommendation ("1 and 2"). This memo independently re-verifies
every claim from source and lays out the decision in more detail, including
cost/risk per option and a fourth option NEEDS-ERIC did not name. Where the
two disagree, treat NEEDS-ERIC's item 10 as the earlier, shorter cut and this
one as the fuller version — they are not in tension.

## What ADR-0009 claims

`docs/adr/ADR-0009-gemma-pinned-for-corpus-generation.md`, status **Accepted**,
"backfilled 2026-08-21, decision dated 2026-08-20":

- **Title (line 1):** "Gemma, pinned by version and seed, generates the corpus,
  for third-party reproducibility"
- **Line 23-25 (Decision):** "**Corpus generation runs on open-weights Gemma,
  pinned by version and seed** (`CONVENTIONS.md:208`, `architecture-spec.md:1220`).
  `CAPABILITY_CARTOGRAPHER` runs on the same footing (`architecture-spec.md:138`)."
- **Line 34-36, scripted verbatim for the demo video:** *"the attack corpus is
  generated by an open-weights model pinned by version and seed, because a
  corpus you can't regenerate is a corpus you can't pre-register."* The ADR
  calls this "the only [rationale] that may be written anywhere."
- **Line 38-39:** "Gemma also carries **+0.2 of the +0.6 additional-model
  bonus**, which is why it has a real architectural home rather than a
  bolted-on one."
- **Line 61-63 (Consequences):** "**The reproducibility check is the artifact,
  not a screenshot:** Gemma regenerates the corpus from the pinned version and
  seed and the hash matches, **twice, from a clean process**."
- **Line 68-70:** lists Gemma as cut candidate 2, warning that cutting it
  "loses 0.2 of the ceiling, the second-model story, and **third-party
  reproducibility of the corpus**."

In short: ADR-0009 asserts, as an accepted architectural fact, that a
specific model (Gemma, pinned by version and seed) generated the 48+ attack
instances that make up the CRUCIBLE corpus, that this is independently
verifiable by re-running it, and that this claim is worth 0.2 of the
contest's model-diversity bonus. All of that is scripted to be spoken on
camera.

## What is actually true

**1. Gemma appears in zero executable code.**
`grep -rin "gemma" . --include=*.py --include=*.json --include=*.yaml --include=*.sh`
returns no hits at all outside `docs/` and `planning/`. Every one of the ~30
hits for "gemma" in the repo is in a Markdown doc (ADRs, specs, `NEEDS-ERIC.md`,
`competitive-analysis.md`) or in `scripts/make-lane-briefs.py:177`, which is a
static string literal in a lane-brief generator (`"Yes — Gemma, pinned by
version and seed, for corpus generation only."`) — itself just more prose,
not a call to any model.

**2. `CAPABILITY_CARTOGRAPHER`, the architectural home the ADR cites, has no
module.** `grep -rn "CAPABILITY_CARTOGRAPHER" .` returns only doc hits. This
is independently confirmed in-repo at `docs/diagrams/architecture.md:17`:
*"**Not built.** No module under `crucible/` matches it. Capability mapping
today is the deterministic path in `target/refund_agent/capabilities.py`
plus a human-ratified manifest."* — and again at `docs/diagrams/architecture.md:434`.

**3. The corpus was hand-authored by lane agents, in git, with commit
messages that say so.** `git log --oneline --all -- corpus/`:

```
26e3ba0 L2(b): the checks that must run on the corpus, before the corpus exists
639c4be corpus: author attack families F1 and F2, with four near-miss benigns
5815ff8 corpus: F3 and F5, sixteen attacks and four near-misses
70f6125 corpus: F6 and F7, sixteen attacks and four near-misses
86a9a29 corpus: author the F4 sealed held-out family, 24 destination-smuggling instances
cfd9daa corpus: the twelve ordinary benign fixtures and the pair records
...
2e459a6 corpus: make CAP_INVOKES_AGENT reachable. PARKED -- breaks two frozen counts.
```

Every message says "author," never "generate." No commit mentions Gemma,
a model, or a generation run.

**4. No corpus instance carries a generator, seed, model, or provenance
field of any kind.** Read `corpus/training/F1-01-chargeback-band-override.json`
in full — its top-level keys are:

```
['slug', 'kind', 'family', 'sealed', 'capability_classes', 'tool_fqname',
 'approver', 'scored_features', 'scenario', 'trace', 'input_turns',
 'abuse_pattern', 'policy_sections_violated', 'breach_note']
```

`grep -rli "generator|\"seed\"|provenance|\"model\"" corpus/training/*.json`
returns **zero matches** across all 48 training instances. `corpus/schema.py`,
`corpus/model.py`, and `corpus/F4-MANIFEST.json` were also checked — the one
"seed" hit in `schema.py` is prose about "seeding the corpus twice" (a dedup
warning), not an RNG seed field. `corpus/README.md` does not mention Gemma at
all.

**5. Nobody has ever run a Gemma corpus-generation job.** There is no Cloud
Run service for it (`docs/CONVENTIONS.md` §3.3 describes the hosting plan —
Cloud Run + NVIDIA L4, `min-instances=0`, ~$0.34/burst — in future tense, as
a decision, not a deploy log), no billing line for it (per `docs/NEEDS-ERIC.md`
item on the $160 spend alert, nothing in `docs/ops/billing.md` references a
GPU burst), and no artifact anywhere claiming a hash match from a
regeneration run.

**Net: every factual claim in ADR-0009's Decision and Consequences sections
is false as of 2026-08-21.** The corpus exists, is real, is committed, and is
sealed — none of that is in question. What is false is specifically that
Gemma produced it, that it is reproducible by a third party running Gemma,
and that this earns the +0.2 model-diversity bonus.

**What does NOT break as a result** (worth stating plainly, per
`docs/NEEDS-ERIC.md` item 10): the pre-registration claim does not actually
rest on regenerability. It rests on the commitment hash (`2cde0250de00e692`,
per the session state block in this repo's `CLAUDE.md`), the public commit
timestamp, and the IAM boundary that keeps the Armorer from reading or
writing the sealed corpus. Those three are real, independent of how the
instances were originally written, and unaffected by whichever option below
is chosen.

## The options

### (a) Supersede ADR-0009, drop the Gemma claim entirely
**Cost:** ~1-2 hours. Write a new ADR (this repo supersedes rather than edits —
see Constraints) stating the corpus was hand-authored by lane agents,
hash-locked, and committed before the loop runs; the pre-registration claim
rests on the commitment hash + IAM boundary, not on regenerability. Strike
the Gemma line from the demo script (`execution-spec.md:532`), `CONVENTIONS.md`
§3.2/§3.3, `architecture-spec.md`, `build-spec.md`, `docs/lanes/L2-target-corpus.md`,
and `planning/competitive-analysis.md`. `BUILD-LIST.md` and `CONTEST.md`
already need only the bonus line corrected to "not attempted."
**Wins:** Removes the false claim everywhere, including the one place that
matters most (the video script). Costs nothing else — the pre-registration
argument survives on the hash/IAM mechanism alone, which was already doing
the real work. Lowest-risk option with ten days left.
**Risk:** Gives up 0.2 of a 0.6 bonus ceiling (a full point on a 1-6 scale
is 20% of the maximum score per `CONTEST.md`, so 0.2 is about 3.3% of the
ceiling) and drops the "second Google model" story entirely — CRUCIBLE would
then use exactly one Google model family (Gemini, in three tiers) plus
whatever Vertex reranking/etc. already exists.
**Can it land before deadline?** Yes, trivially — it's pure documentation and
one script edit, no code risk.

### (b) Actually build the Gemma path so the claim becomes true
**Cost:** Real, and larger than it looks. `CAPABILITY_CARTOGRAPHER` has no
module — building it means: standing up the Cloud Run + L4 service per
`CONVENTIONS.md` §3.3, writing the actual capability-classification inference
code, wiring pinned-version-and-seed generation for the corpus (or at minimum
for `CAPABILITY_CARTOGRAPHER`'s narrower per-tool job), running it against
the sealed corpus without contaminating the existing hand-authored instances
or invalidating the already-committed hash `2cde0250de00e692`, and proving
the reproducibility claim twice from a clean process (the ADR's own bar).
Given the corpus is already authored, sealed, and hash-committed, replacing
it with Gemma-generated instances this late risks re-opening the D5 corpus
freeze and the SEP-BY 21/3 measurements that depend on the current 48/24/24/9
counts — those are exactly the "frozen counts" that `corpus/C6-reach` is
already parked for breaking.
**Wins:** Earns the +0.2 honestly, keeps the two-Google-model story, and (if
scoped to `CAPABILITY_CARTOGRAPHER` rather than full corpus regeneration)
gives Gemma a real, non-decorative architectural job — which is what the
Constraints for this memo and the build-spec both insist on: no bolted-on
model integration.
**Risk:** Highest of the three. Ten days left, solo, with a corpus freeze
that (per this repo's own state) "must land before the first patch is
written" and a code freeze on 08-28. Standing up a new GPU service, writing
new inference code, and touching the corpus is the kind of scope that eats
the days meant for the actual patch-and-regression loop — the loop that has,
as of this memo, never been run once. Building Gemma before the loop exists
risks delivering a scored bonus feature for a project that never produced
its core scored numbers.
**Can it land before deadline?** Only if scoped narrowly to
`CAPABILITY_CARTOGRAPHER` running at attach-time on the *existing* corpus's
tools (not regenerating corpus instances) — that's a bounded, per-tool
classification job, not a corpus-authoring job. Full corpus regeneration by
Gemma is very unlikely to land safely given the freeze dependencies.

### (c) Narrow the claim to something true and still useful
**Cost:** ~2-4 hours. Keep Gemma in the architecture as `CAPABILITY_CARTOGRAPHER`
only (a real, scoped, unclaimed job per `architecture-spec.md:138-140`) without
claiming it touched the corpus. Supersede ADR-0009 with a version that says:
corpus generation is hand-authored and hash-committed (true); Gemma is
integrated as the capability classifier for tools the deterministic pre-pass
can't resolve (true, once built — see below); drop the reproducibility
argument for the corpus specifically. This still requires *building*
`CAPABILITY_CARTOGRAPHER` on Gemma to be honest — it's option (b) narrowed to
its safest slice, not a documentation-only fix.
**Wins:** Smallest real build that still earns the +0.2 legitimately, without
touching the frozen corpus at all. `CAPABILITY_CARTOGRAPHER`'s job (propose
capability classes per tool, from docstring/schema, human-ratified downstream
per `CONVENTIONS.md:97`) is bounded, low-volume ("per tool, attach only"),
and doesn't interact with the sealed corpus, the hash, or SEP-BY at all — the
things ten days is too tight to risk.
**Risk:** Still new code, new Cloud Run service, new integration surface,
ten days out, on top of a project that hasn't run its primary loop yet. Lower
risk than (b) but not free, and it's still work spent on a bonus 0.2 rather
than on the deliverables that are pass/fail (per `docs/contest/BUILD-LIST.md`,
the architecture diagram and README already closed; Cloud Run deploy proof is
still open and IS pass/fail, unlike this).
**Can it land before deadline?** Plausibly, if started immediately and capped
strictly to the Cartographer's stated scope — but it competes directly for
time against the Cloud Run deploy proof (pass/fail, already flagged as the
most-slipped Day-2 item) and the first real loop run (which produces every
other number this project needs to report).

### (d) Not previously named: fix the claim now (a), leave Gemma as an explicitly tracked stretch goal for (b)/(c) only if the pass/fail items and the first loop run land early
**Cost:** Same ~1-2 hours as (a) up front, zero committed cost beyond that.
**Reasoning:** (a) and (b)/(c) are not mutually exclusive in sequence — the
false claim must be corrected regardless of what happens to Gemma, and
correcting it does not foreclose building the Cartographer later if time
allows. The mistake would be treating "fix the doc" and "decide Gemma's
fate" as one decision that has to be made once, under time pressure, before
Sat 08-22's target freeze. It doesn't. Do (a) now, unconditionally. Then, if
and only if the Cloud Run deploy proof is verified working and the first loop
run has produced real numbers with days to spare before the 08-28 code
freeze, revisit (b)/(c) as a genuine stretch goal with a hard go/no-go date
attached (e.g., "attempt only if both are true by 08-26; otherwise the +0.2
is foregone and that's fine").
**Wins:** Removes deadline pressure from a decision that doesn't need to be
made under pressure. The false claim gets fixed today either way. The
possibility of the honest +0.2 stays open without gating it on ten-day
optimism.
**Risk:** None beyond (a)'s own risk (giving up the bonus if the stretch
never gets attempted) — but that's already true of (a) alone, and this
option is strictly a superset of it.
**Can it land before deadline?** The correction: yes, today. The stretch:
conditional, evaluated against real Day-6/7 evidence instead of guessed now.

## Recommendation

**Do (d): fix ADR-0009 today via supersession (the mechanics of option (a)),
and treat `CAPABILITY_CARTOGRAPHER` on Gemma as a conditional stretch goal,
not a commitment.**

Reasoning: the false claim is a live liability the moment it's spoken on
camera or read by a judge, and fixing it costs almost nothing — the
pre-registration argument doesn't need Gemma, it needs the hash and the IAM
boundary, both of which already exist and already work. There is no version
of "wait and decide" that is safer than fixing the doc now; the only thing
worth deliberating is whether to *also* attempt the honest build, and that
decision has better information available on 08-26 than it does today. Ten
days solo, with a corpus freeze still pending, a Cloud Run deploy proof still
unverified (pass/fail, more overdue than this), and the loop never having
run once, is not a context where a new GPU service and new inference code is
the right thing to start today. It might be the right thing to start in five
days, once the numbers that actually decide this contest exist. Don't
foreclose that by guessing now; don't hold the doc fix hostage to that
question either — they're separable, and NEEDS-ERIC item 10 says as much
("1 and 2... are independent, and 1 is required regardless").

This repo supersedes ADRs rather than editing them (per this repo's
`CLAUDE.md`) — whoever implements this should write **ADR-0012 or the next
free number** (check `docs/adr/` for the current max before assigning),
titled something like "Corpus provenance is hand-authored and hash-committed;
Gemma is not integrated," that formally supersedes ADR-0009's Decision
section while keeping ADR-0009 on disk as history, per this project's own
practice of recording superseded values rather than deleting them.
