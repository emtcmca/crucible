4. UNEXPECTED FINDING (KNOWN_ISSUE, out of the original scope, not fixed here)
================================================================================

The ledger dump in section 3 also shows something the task did not ask about
but is directly relevant to L3's exit criterion 1 ("the blocked tool never
appears in the ledger [as executed]") and to core.py's own after_tool
docstring ("Only ever called when the call was allowed"): under a REAL
Runner, a DENY produces BOTH a TOOL_ATTEMPT *and* a TOOL_EXECUTED, and the
denied tool's handle shows up in executed_handles() even though the Python
function never ran.

Root cause, read from functions.py: `_execute_single_function_call_async`
(and its live twin) run "Step 4: plugin after_tool_callback" UNCONDITIONALLY
after Steps 1-3, regardless of whether Step 1 already short-circuited the
call:

    # Step 4: Check if plugin after_tool_callback overrides the function
    # response.
    altered_function_response = (
        await invocation_context.plugin_manager.run_after_tool_callback(
            tool=tool, tool_args=function_args, tool_context=tool_context,
            result=function_response,   # <- the DENY dict, on a denied call
        )
    )

crucible/plugin/adk.py's CruciblePlugin.after_tool_callback does not check
whether the popped attempt was itself a denial before calling
`self.core.after_tool(attempt_event=attempt, result=result)` - so it
faithfully records the plugin's own blocked_result dict as if it were a real
tool result, producing a spurious TOOL_EXECUTED.

This is invisible in test_plugin_enforcement.py because those tests only
call after_tool_callback by hand, and only on the ALLOW branch (see that
file's test_handwritten_patch_compiles_and_the_blocked_tool_never_runs,
which never calls after_tool at all on the DENY path) - so the existing
suite's "DENY -> no EXECUTED" assertion was true of the test harness, not of
the real Runner-driven system.

test_adk_invocation_paths.py's two *_KNOWN_ISSUE tests assert this CURRENT
behavior (so they fail loudly if it's silently changed) rather than
asserting the invariant the rest of the repo currently assumes. This file
does not fix crucible/plugin/adk.py (out of this lane's scope). The fix
belongs in CruciblePlugin.after_tool_callback: skip core.after_tool when the
popped attempt's outcome was a denial (the information is already on hand -
`outcome.allowed` at the point _pending was populated, or equivalently
`attempt["kind"] == TOOL_ATTEMPT and attempt.get("policy_decision") in
(DENY, ...)`).

6. DEMO-RELEVANT VERDICT
================================================================================

The ADK web UI (adk web) can safely appear on camera showing enforcement:
CruciblePlugin.before_tool_callback fires and blocks on BOTH the non-live
run_async path AND the live/streaming run_live path that adk web's
bidirectional mode uses, for google-adk==2.1.0. ADR-0012's stated reason for
restricting the demo to non-live run_async (the callback "reported not to
fire" under live/streaming, citing ADK issue #4704) does not hold for this
installed version - the coordinator should re-open ADR-0012 with this
evidence rather than leave the non-live-only restriction standing on a
premise this probe falsified.

Two caveats that would need to be settled before actually filming adk web,
neither undermines the fire/block answer above:
  - This probe uses a stub model, not adk web's real chat/voice UI wired to
    a live Gemini connection; the UI layer itself was not exercised, only
    the Runner/plugin wiring underneath it. If ADK issue #4704 was actually
    about something UI-specific rather than about the Runner/plugin
    protocol, that would not be caught here - I found no such distinction in
    the source, but I did not find or read the original issue #4704 report
    itself (no network access from this probe), so I cannot confirm what
    specific ADK version or symptom it originally described.
  - Section 4's KNOWN_ISSUE affects the ledger's bookkeeping, not the actual
    block - the real tool body did not run in either DENY case measured. It
    is a correctness bug in how the event gets *recorded* after the fact,
    worth fixing before quoting "TOOL_EXECUTED never appears for a denied
    call" as a measured property of a real Runner-driven run, but it does
    not change today's fire/block verdict.
