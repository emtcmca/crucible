### 00:25 — the batch was KILLED at 9 of 60, and the way it failed is the lesson

`run_in_background` reported the batch as **killed**, not completed. Nine runs had finished,
all exit 0, no `BATCH-DONE` sentinel. Nothing crashed: the harness terminated the
background task.

**The failure mode is the one this project keeps meeting.** A dead batch and a running
batch look identical from outside — no output either way. Had the runner not written a
`BATCH-DONE` sentinel, "no news" would have read as "still going" for seven hours, and
Eric would have woken to nine runs instead of sixty. **Silence is not success.**

Two fixes:

1. **Relaunched fully detached** via `Start-Process`, so the batch's lifetime is no longer
   tied to a harness-managed task. PID recorded in `BATCH.pid`. The runner was already
   resumable — a run that has written an exit code is skipped — so the restart cost
   nothing and picked up at run 10.
2. **Armed a monitor that watches for the right things.** It reports any non-zero exit
   immediately, a progress line every ten runs, `BATCH-DONE` on completion, and — the one
   that matters — **the process disappearing without a `BATCH-DONE`**. A monitor that only
   watched for success would have stayed silent through exactly the failure that just
   happened.
